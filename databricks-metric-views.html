The root cause isn't SQL skill

  • The definition of "revenue" lives in every consumer, not in one place.
  • Each copy silently drifts: a filter here, a join there.
  • Ratios (AOV, revenue per customer) break the moment someone rolls them up.
  • Nobody can answer "which one is right?" without reading three SQL files.
The fix: move the definition into a governed object, and let the query engine decide the grain. That object is a metric view.

What stays the same

Your gold tables, your ETL, your dashboards. A metric view sits on top — it is a definition layer, not a new pipeline.

Use a real example from our own stack here instead of the generic numbers if you have one — it lands much harder. The ratio point is the one that convinces engineers: averages of averages are wrong and nobody notices.
Concept

What is a metric view?

Definition: a Unity Catalog object that stores a semantic model in YAML — a source, its joins, the fields you can group by, and the measures you can aggregate — with no fixed grain.
  • Aggregation is resolved at query time. Define sum of revenue ÷ distinct customers once; group by country, month, or nothing at all — it stays correct.
  • It's a first-class UC object. Same catalog.schema.name, same GRANT SELECT, same lineage and tags as a table.
  • It's text. The definition is YAML inside DDL, so it belongs in Git and goes through PR review.
  • One definition, many consumers. SQL, AI/BI dashboards, Genie, and external BI tools all read the same model.

Mental model

A normal view answers one question. A metric view answers a family of questions.

Emphasise "no fixed grain" — that is the entire idea. Everything else is packaging. If someone asks "is this a cube?": no, nothing is precomputed by default; materialization is an optional optimisation.

skeletonYAML

  - name: customer

    'on': o_custkey = c_custkey

  - name: market_segment
    expr: customer.c_mktsegment

  - name: total_revenue
    expr: SUM(o_totalprice)

The one rule that separates them

Fields must not be aggregated. Measures must always be aggregated. If you can't decide which one something is, ask: "would a user ever GROUP BY this?"

Both are composable

A field can reference an earlier field; a measure can reference earlier measures via MEASURE(). Build atomic first, then layer.

Walk left to right. Point out that unaggregated numerics (e.g. list price) are fields, not measures — users may want to bucket by them.

In one line: a standard view ships rows; a metric view ships meaning.
The "ratios" row is the technical argument, the "metadata for AI" row is the argument for the Genie stakeholders. Don't oversell — the last row matters: standard views are still the right tool for extracts and reshaping.
Judgement

Reach for a metric view when…

✓ Good fit

  • The number appears in more than one dashboard, deck or Slack thread.
  • People slice it by different dimensions — month, region, segment, channel.
  • It's a ratio or a distinct count that keeps getting rolled up wrongly.
  • You want Genie to answer questions about it in natural language.
  • You need one auditable definition for finance or regulatory reporting.

✗ Use a standard view instead

  • Row-level extracts — you need the individual records, not aggregates.
  • Fact-to-fact or many-to-many joins — pre-join in a UC view, then point the metric view at that.
  • ML feature tables — features want a fixed, reproducible grain.
  • A genuinely one-off question — don't create a governed object for a Tuesday.
Rule of thumb: if you'd be annoyed to find two versions of it, it belongs in a metric view.
The fact-to-fact restriction is the most common design mistake — call it out now so it doesn't surprise them at build time. We'll repeat it on the pitfalls slide.
Construction · Step 0

Before you write any YAML

Platform

Unity Catalog enabled. A SQL warehouse (or UC-enabled compute) on a current runtime — confirm your workspace's version supports spec 1.1.

Permissions

SELECT on every referenced table, plus CREATE VIEW (or ownership) on the target schema.

Pick the right source — this decides everything downstream

  • Point at a curated gold fact, never bronze. A metric view inherits every quality problem underneath it.
  • Confirm the grain of the source in one sentence: "one row per order line." Write it in the comment.
  • Check the joins are truly many-to-one before you model them.
the wrapperSQL
CREATE OR REPLACE VIEW
  main.gold.mv_sales_analytics
WITH METRICS
LANGUAGE YAML
AS $$
version: 1.1
source: ...
$$;

Naming convention

We'll prefix ours mv_ and keep them in the same schema as the gold facts they model.

Note the $$ delimiters — everything between them is YAML, and YAML is whitespace-sensitive, so the indentation must be consistent. Editors that reformat SQL have been known to mangle it; keep the DDL in a .sql file in Git.
Construction · Step 1

Source & global filter

source · filter · commentYAML
version: 1.1

source: SELECT * FROM main.gold.fct_orders

filter: o_orderdate >= '1995-01-01'

comment: |-
  Order performance. Grain: one row per order.
  Owner: Analytics Team · Reviewed: 2026-07-31
Careful: filter applies to every query against the view, forever. It is for hard scope rules — exclude test orders, exclude soft-deleted rows — never for "this dashboard's date range."

What source accepts

A table, view, materialized view, streaming table, an inline SQL query — or another metric view, which is how you layer a semantic model.

Always fill in comment

State the grain, the owner and the review date. It surfaces in Catalog Explorer and gives Genie context.

Parameters (optional)

Declare runtime inputs and call the view as a function:
FROM mv_sales(discount => 0.1)

Ask the room: what is currently hard-filtered in our gold views that should actually be a metric-view filter? Usually it is "status not in cancelled/test".
Construction · Step 2

Joins — many-to-one, always

joins · nested joinsYAML
joins:
  - name: customer
    source: main.gold.dim_customer
    'on': o_custkey = c_custkey
    at_most_one_match: true
    joins:
      - name: nation
        source: main.gold.dim_nation
        'on': c_nationkey = n_nationkey

# reference it later as:
#   customer.c_mktsegment
#   customer.nation.n_name
  • Joins are LEFT OUTER from the fact to a dimension. Rows in the fact are never dropped.
  • Nest joins to model snowflake schemas, then reference with dotted paths.
  • at_most_one_match: true is an optimisation. Set it only when the relationship really is many-to-one — if it fans out, your measures are silently wrong.
Fact-to-fact? Stop. Metric-view joins can't express many-to-many. Build a pre-joined view in Unity Catalog and use that as the source.

YAML gotcha

Quote the key: 'on':. Unquoted, YAML parses on as the boolean true and the join silently loses its condition.

Verify cardinality with a quick check before enabling at_most_one_match: SELECT o_custkey, COUNT(*) FROM dim GROUP BY 1 HAVING COUNT(*) > 1. If that returns rows, don't set the flag.
Construction · Step 3

Fields — everything users slice by

fieldsYAML
fields:
  - name: order_date
    expr: o_orderdate
    display_name: Order Date

  - name: order_month
    expr: "DATE_TRUNC('MONTH', order_date)"
    display_name: Order Month

  - name: order_status
    expr: |-
      CASE o_orderstatus
        WHEN 'O' THEN 'Open'
        WHEN 'F' THEN 'Fulfilled'
      END
    display_name: Order Status
    synonyms: [status, fulfilment status]

  - name: market_segment
    expr: customer.c_mktsegment
    display_name: Market Segment
  • Ship multiple date grains. Date, month, quarter, year as separate fields — don't make analysts write DATE_TRUNC.
  • Fields can reference fields. order_month is built from order_date, not from the raw column.
  • Decode codes into labels with CASE. Nobody should have to know that 'F' means fulfilled.
  • Unaggregated numerics are fields, not measures — users may want to bucket by them.
name vs. display_name: name is the API — dashboards and saved queries bind to it, so treat it as permanent. display_name is the label; change it freely.
Synonyms are cheap and pay off enormously in Genie — every business alias someone might type. Add them at build time, not after the first complaint.
Construction · Step 4

Measures — four kinds you'll actually use

1 · Atomic

A plain aggregate over source columns. Build these first.

2 · Filtered

Same aggregate, scoped with FILTER (WHERE …).

3 · Composed

Built from other measures via MEASURE(). Ratios go here.

4 · Window

Rolling, cumulative or semi-additive, via window:.

measuresYAML
measures:
  - name: total_revenue                        # 1 atomic
    expr: SUM(o_totalprice)
    display_name: Total Revenue
    format: {type: currency, currency_code: USD}
    synonyms: [revenue, sales]

  - name: order_count                          # 1 atomic
    expr: COUNT(DISTINCT o_orderkey)

  - name: open_order_revenue                   # 2 filtered
    expr: SUM(o_totalprice) FILTER (WHERE o_orderstatus = 'O')

  - name: avg_order_value                      # 3 composed
    expr: MEASURE(total_revenue) / MEASURE(order_count)
    synonyms: [AOV]

  - name: t7d_customers                        # 4 window
    expr: COUNT(DISTINCT o_custkey)
    window:
      - order: order_date
        semiadditive: last
        range: trailing 7 day
Hard rule: every expr must be an aggregate. A bare column is a field, not a measure.

No raw OVER ()

Inline SQL window functions aren't allowed in expr. Use the declarative window: block instead — that's what makes rolling metrics re-aggregate correctly.

Never hand-roll a ratio

Write MEASURE(a)/MEASURE(b). Writing SUM(x)/COUNT(y) directly re-derives logic and will drift from the atomic measures.

Composed measures are the payoff of the whole feature — AOV is correct at country grain, month grain and grand total without anyone rewriting it. Demo that live if there's time.
Construction · Complete

The whole thing, end to end

① wrapper · source · joinsSQL + YAML
CREATE OR REPLACE VIEW main.gold.mv_sales_analytics
WITH METRICS
LANGUAGE YAML
AS $$
version: 1.1
source: SELECT * FROM samples.tpch.orders
filter: o_orderdate >= '1995-01-01'
comment: |-
  Sales analytics for order performance.
  Grain: one row per order. Owner: Analytics Team
joins:
  - name: customer
    source: samples.tpch.customer
    'on': o_custkey = c_custkey
    at_most_one_match: true
    joins:
      - name: nation
        source: samples.tpch.nation
        'on': c_nationkey = n_nationkey
② fields · measures  (same block, continued)YAML
fields:
  - name: order_month
    expr: "DATE_TRUNC('MONTH', o_orderdate)"
    display_name: Order Month
  - name: market_segment
    expr: customer.c_mktsegment
    display_name: Market Segment
    synonyms: [segment, industry]
  - name: customer_nation
    expr: customer.nation.n_name
    display_name: Country
measures:
  - name: total_revenue
    expr: SUM(o_totalprice)
    display_name: Total Revenue
    format: {type: currency, currency_code: USD}
  - name: order_count
    expr: COUNT(DISTINCT o_orderkey)
    display_name: Order Count
  - name: avg_order_value
    expr: MEASURE(total_revenue) / MEASURE(order_count)
    display_name: Avg Order Value
    synonyms: [AOV]
$$;

Read it top to bottom

Scope → context → what you slice by → what you compute. Every metric view we build has exactly this shape.

Then grant it

GRANT SELECT ON VIEW main.gold.mv_sales_analytics TO `analysts`;

Ship it as code

Lives in Git, reviewed in a PR, deployed by CI — not pasted into a notebook.

Consumption

Querying: the MEASURE() rule

group by anythingSQL
SELECT
  customer_nation,
  order_month,
  MEASURE(total_revenue)   AS revenue,
  MEASURE(order_count)     AS orders,
  MEASURE(avg_order_value) AS aov
FROM main.gold.mv_sales_analytics
GROUP BY ALL
ORDER BY revenue DESC;
drop a dimension — nothing else changesSQL
SELECT MEASURE(avg_order_value) AS aov
FROM main.gold.mv_sales_analytics;   -- still correct
Wrap measures, never fields. MEASURE(total_revenue) ✓ · MEASURE(order_month) ✗ · bare total_revenue ✗
  • GROUP BY ALL saves you maintaining the list by hand.
  • Filter on fields in WHERE exactly as you would on a table.
  • Pass parameters by calling it as a function: FROM mv_sales(discount => 0.1).
  • Metric views can't be joined to tables or to each other — compose inside the YAML instead.

The point

Between those two queries, no metric logic changed. The engine re-derived AOV from its atomic parts at a new grain. That's the whole feature.

Run both queries live if you can. The second one — AOV with no GROUP BY — is the moment people understand why this isn't just a view with extra steps.
Consumption

One definition, four front doors

SQL & notebooks

Query it like a table. Analysts get governed metrics without reading anyone's CTEs.

AI/BI dashboards

Pick the metric view as the dataset; fields and measures appear as ready-made building blocks with their formats applied.

Genie

display_name, synonyms and comment are what make natural-language answers land. Metadata quality = answer quality.

External BI

Power BI, Tableau and friends connect through BI compatibility mode and see the same measures.

Why this matters: the four consumers can no longer disagree. Fixing a definition once fixes it everywhere — no dashboard sweep.

Optional: materialization

Pre-aggregate hot combinations for speed. Note that non-additive measures (COUNT(DISTINCT), median, percentiles) can't be re-aggregated from a partial result — they need an exact grain match.

Materialization is an optimisation, not a starting point. Ship the view first, measure query latency, then decide.
Best practice

Eight habits that keep this clean

1

One view per business process

Orders, shipments, claims. Not one monolith with 200 measures nobody trusts.

2

Source from governed gold

Never bronze. A metric view inherits every upstream quality defect and gives it a friendly name.

3

Atomic first, then compose

Define total_revenue and order_count before avg_order_value. Never re-derive a ratio.

4

Treat name as an API

Dashboards bind to it. Rename display_name freely; changing name is a breaking change.

5

Metadata is not optional

display_name, synonyms and format on every measure a human or Genie will ever see.

6

Version it in Git

The DDL is text. PR review, CI deploy, one owning team with CREATE, everyone else SELECT.

7

Prove join cardinality

Run the duplicate check before setting at_most_one_match: true. Fan-out corrupts silently.

8

Validate against the old number

Reconcile the new measure to the dashboard it replaces before you cut anyone over.

Habit 8 is non-negotiable for us — every migration lands with a reconciliation query in the PR description showing old vs new for at least three grains.

Errors you'll hit, and what they mean

SymptomActual causeFix
Can't resolve the measureYou selected a measure without wrapping itWrap it: MEASURE(total_revenue)
Numbers inflate when you add a dimensionJoin fan-out — the "dimension" isn't unique on the keyVerify cardinality; unset at_most_one_match; pre-join in a UC view
YAML parse error near the joinon was parsed as the boolean trueQuote the key: 'on':
Window function not supportedRaw SUM(…) OVER (…) inside exprUse the declarative window: block
Ratio is wrong at rollupRatio hand-written over raw columns instead of composedMEASURE(a) / MEASURE(b)
Can't join it to another tableMetric views aren't joinable — by designModel the join inside the YAML, or below in a source view
Suddenly slow after materializingNon-additive measure needs an exact grain matchMaterialize the grains actually queried, or accept live compute
The dangerous one is row two. It doesn't throw an error — it returns a bigger, wrong number. Always reconcile after adding a join.
Tie row two back to our own history: silent wrong-data bugs are far more expensive than loud failures. Reconciliation is how we catch them.

Recap

Three things to remember

1

No fixed grain

A measure is defined without a GROUP BY. The engine resolves it per query — that's what makes ratios stay correct.

2

Fields slice, measures compute

Fields are never aggregated; measures always are. Every modelling decision comes back to this split.

3

It's code, and it's governed

YAML in Git, reviewed in a PR, granted in Unity Catalog. Treat it with the same care as a production table.
