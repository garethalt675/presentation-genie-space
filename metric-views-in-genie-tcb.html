Powering a Genie Space:
Metric Views vs. Views & Tables

Two ways to give Genie the business meaning behind our data — what each one actually does, which questions each gets right, and how to choose.

Method A · Tables & Views Method B · Metric Views Compare & Contrast ~45 min
Frame the session as a decision, not a product tour. Everyone in the room either owns a Genie space or is about to. The question they came with is "why are my Genie answers inconsistent" — both methods are answers to that, with different costs.
The problem

Same question, three sessions, three numbers

₫4.2bn
"Average order value by segment"
Genie used AVG(total_price)
₫4.7bn
"AOV per customer segment"
joined a dimension that fanned out
₫3.9bn
"What's our AOV this quarter?"
calendar quarter, not fiscal

Genie did nothing wrong

  • It wrote valid SQL against exactly what we gave it.
  • Nobody had told it that AOV means revenue ÷ distinct orders, not the average of a column.
  • Nobody had told it which join is safe, or that our quarter starts in October.
  • Every rephrasing is a fresh chance to guess differently.
The real question: where should business meaning live — in instructions we write to Genie, or in the data model itself?

That's the whole session

Method A puts meaning in the space. Method B puts meaning in Unity Catalog. Both work. They fail differently.

Substitute a real TCB example if you have one — a metric two teams report differently. The point to land: this is not a Genie defect, it is a semantics gap, and semantics is our job not the model's.
Foundation

What Genie actually does with your question

01
You ask

Natural language, in the chat panel. No SQL.

→
02
Genie reads context

Asset names, column comments, synonyms, instructions, example SQL — and metric view fields & measures.

→
03
Genie writes SQL

It picks the tables, the joins, the filters and the aggregation.

→
04
Runs & shows

Executes under your Unity Catalog permissions and returns the SQL alongside the answer.

Step 2 is the only step we control

We cannot change how the model reasons. We can only change what it is allowed to read. Every technique in this session — comments, synonyms, example SQL, metric views — is a way of loading step 2.

Genie is a SQL writer, not a calculator

If the definition of a metric isn't discoverable, Genie infers one. It will be plausible, confidently presented, and sometimes wrong.

Good news: it shows its working

The generated SQL is always visible. Reviewing it is how we audit — and how we spot which method is being used.

Encourage the habit of expanding the SQL on every answer during rollout. That is how the team builds intuition for what Genie can and can't infer, and it is the fastest way to find missing metadata.
The choice

Two ways to hand Genie our semantics

Method A

Tables & views, curated in the space

Point Genie at the gold tables or SQL views, then teach the space: column comments, agent synonyms, text instructions, and example SQL queries.

Meaning lives in: the Genie space configuration.

Owned by: whoever curates that space.

Scope: one space at a time.

Method B

A metric view as the semantic layer

Model the business logic once in Unity Catalog — measures, fields, joins, synonyms — then point Genie at that single object.

Meaning lives in: Unity Catalog, as versioned YAML.

Owned by: the data team, via pull request.

Scope: every space, dashboard and query at once.

Not either/or. Most mature spaces run both — we'll come back to the hybrid pattern at the end. But you should know which one is carrying the weight.
Resist the temptation to declare a winner here. People need to see the mechanics of both before the comparison table lands. Say explicitly: "if you already have a working space on Method A, nobody is asking you to tear it down today."
Method A · Tables & views

What you configure in the space

1

Pick the assets

Add the gold tables or views. A space supports up to 30 tables — but the guidance is five or fewer. Every extra asset is another way to pick wrong.

2

Document the columns

Clear names and comments in Unity Catalog. Add agent-scoped synonyms and custom descriptions so Genie maps "doanh thu", "revenue" and "sales" to the same column.

3

Add SQL expressions

Define metrics and filters as SQL snippets. This is the strongest lever available in Method A.

4

Add example SQL queries

Show Genie how to answer the complex, multi-step or ambiguous questions. These double as trusted, reviewable assets.

5

Write text instructions — last

Plain-English rules. Databricks is explicit: use these only as a last resort.

example SQL you'd registerSQL
-- Q: "average order value by segment"
SELECT
  c.c_mktsegment AS segment,
  SUM(o.o_totalprice)
    / COUNT(DISTINCT o.o_orderkey) AS aov
FROM gold.fct_orders o
JOIN gold.dim_customer c
  ON o.o_custkey = c.c_custkey
WHERE o.o_status <> 'CANCELLED'
GROUP BY 1;
Notice what this is: the correct definition of AOV, written out — but bound to one phrasing of one question. Ask it by month instead and Genie is improvising again.
Step 5 is the one teams over-invest in because it feels fastest. Text instructions are the most fragile lever — they compete with each other, they're unversioned, and they scale badly past a dozen. Say this plainly.
Method B · Metric views

What a metric view hands Genie

one Unity Catalog objectSQL + YAML
CREATE OR REPLACE VIEW tcb.gold.mv_sales
WITH METRICS LANGUAGE YAML AS $$
version: 1.1
source: SELECT * FROM tcb.gold.fct_orders
filter: o_status <> 'CANCELLED'
comment: Order performance. Grain: one row per order.
joins:
  - name: customer
    source: tcb.gold.dim_customer
    'on': o_custkey = c_custkey
fields:
  - name: market_segment
    expr: customer.c_mktsegment
    display_name: Market Segment
    synonyms: [segment, industry, phan khuc]
  - name: order_month
    expr: "DATE_TRUNC('MONTH', o_orderdate)"
    display_name: Order Month
measures:
  - name: total_revenue
    expr: SUM(o_totalprice)
    display_name: Total Revenue
    synonyms: [revenue, sales, doanh thu]
  - name: order_count
    expr: COUNT(DISTINCT o_orderkey)
  - name: avg_order_value
    expr: MEASURE(total_revenue) / MEASURE(order_count)
    display_name: Avg Order Value
    synonyms: [AOV, average order value]
$$;
  • Measures have no fixed grain. AOV is defined once and stays correct by segment, by month, or overall.
  • Fields are the safe grouping list. Genie doesn't have to guess which columns are dimensions.
  • Joins are declared and constrained — Genie can't invent a fan-out.
  • Synonyms are imported automatically. Up to 10 per field or measure, which is where our Vietnamese business vocabulary goes.
  • The filter is permanent. Cancelled orders can't come back, in any question, in any space.
One asset, whole star schema. Orders + customer collapse into a single thing Genie has to choose — and it comes pre-labelled.
Point at the synonyms lines specifically — bilingual vocabulary is a real TCB advantage here and it's cheap to add. Ten synonyms per field is generous; use them.

Worked example

“What was our average order value by segment?”

Method A — Genie must infer five things
SQL Genie is likely to writeSQL
SELECT
  c.c_mktsegment,
  AVG(o.o_totalprice) AS avg_order_value
FROM gold.fct_orders o
JOIN gold.dim_customer c
  ON o.o_custkey = c.c_custkey
GROUP BY 1;

Three defects, none of them visible

1. AVG(price) ≠ revenue ÷ distinct orders.
2. Cancelled orders were never excluded.
3. If a customer has two rows, the join inflates the average.

Method B — nothing left to infer
SQL Genie writesSQL
SELECT
  market_segment,
  MEASURE(avg_order_value) AS aov
FROM tcb.gold.mv_sales
GROUP BY ALL;

Why it's right

The ratio, the cancelled-order filter and the join safety are all inside mv_sales. Genie only had to choose a dimension and a measure — the two things it's genuinely good at.

And ask it by month instead: the same measure re-derives correctly. No new example query.
The Method A SQL here is realistic, not a strawman — AVG of a price column is the single most common thing an LLM produces for "average order value". Show a real one from our own space if you have a screenshot.
Honest assessment

How each method fails

Method A fails when…
  • The question is phrased in a way your example queries don't cover.
  • A ratio gets rolled up — averages of averages pass silently.
  • The star schema grows and the space drifts past five assets.
  • Two instructions contradict each other and nobody notices which won.
  • A second space needs the same metric — and re-derives it slightly differently.
  • Someone edits the space config; there's no diff, no reviewer, no history.
Method B fails when…
  • Users want row-level detail — "show me order 12345". A metric view only aggregates.
  • The question needs a dimension nobody modelled. That's a YAML change, a PR, a deploy.
  • The relationship is fact-to-fact or many-to-many — must be pre-joined in a view first.
  • Someone tries to join it to another table or metric view. Not supported.
  • Exploration is genuinely open-ended and the questions aren't known yet.
  • The underlying gold table is wrong — a metric view gives bad data a trustworthy name.
Read the asymmetry: Method A fails quietly, with a confident wrong number. Method B fails loudly — the question simply can't be answered until someone models it. For regulated reporting, loud is what we want.
This slide buys credibility for the recommendation later. Do not skip it. The "fails quietly vs fails loudly" distinction is the strongest single argument in the deck for a bank.
Decision

Choosing per space

If the space is for…Start withBecause
Governed KPIs — revenue, NIM, CASA ratio, AOVMetric viewOne definition, auditable, correct at every grain
An executive or regulatory audienceMetric viewAnswers must be defensible and reproducible
The same metric across many spacesMetric viewDefine once; every space inherits it
Operational lookups & record detailViews & tablesMetric views can't return rows
Open-ended exploration of new dataViews & tablesYou don't yet know what to model
A one-off, short-lived spaceViews & tablesNot worth a governed object
Mixed — KPIs plus drill-downBothThe hybrid pattern, two slides from now
Default for our team: if the number appears in more than one report, or anyone outside the team quotes it, it belongs in a metric view.
Adjust the metric names in row one to whatever our actual top KPIs are — CASA ratio and NIM are placeholders, swap in the real ones from the management pack.
Principle

Databricks' own order of preference

1 · SQL expressions
Define metrics, filters and dimensions as SQL
2 · Example SQL queries
Teach complex, multi-step or ambiguous questions
3 · Text instructions
Plain English — last resort only
Structure beats prose. The more of your meaning is expressed as SQL and metadata rather than sentences, the more reliably Genie reproduces it.

A metric view is tier 1 — institutionalised

Every measure is a SQL expression, permanently attached to the data, reusable by every consumer. You're not writing tier-1 guidance per space; you're writing it once.

Method A pushes you down the pyramid

Without a semantic layer, the gaps get filled with example queries and — eventually — paragraphs of text rules. That's the weakest, least reviewable tier.

Tier 2 never goes away

Even with a metric view, keep example SQL for genuinely multi-step questions. The pyramid is a priority order, not an exclusion.

This is the slide to use when someone pushes back with "can't we just write better instructions?" The answer is: yes, and that's tier 3, and it's the tier the vendor tells you to avoid.
How-to

The metadata that actually moves accuracy

agent-facing metadata on a metric viewYAML
fields:
  - name: order_date
    expr: o_orderdate
    display_name: Order Date
    format:
      type: date
      date_format: year_month_day
    synonyms:
      - order time
      - date of order
      - ngay dat hang

measures:
  - name: total_revenue
    expr: SUM(o_totalprice)
    display_name: Total Revenue
    format:
      type: currency
      currency_code: VND
    synonyms: [revenue, total sales, doanh thu]
Now this works: "show me revenue by order time" — no column name in sight.

synonyms — the highest-leverage field

Up to 10 per field or measure, 255 characters each. Imported into Genie automatically. Put every alias the business actually says here, in both languages.

display_name

Max 255 characters. Replaces the technical name everywhere a human sees it — chat answers, dashboards, Catalog Explorer.

comment

On the view and on individual entries. State the grain and the owner. This is Genie's context for when to use something.

format

Currency, percentage, date, number. Stops Genie returning ₫ figures as bare decimals.

The bilingual synonym point is worth dwelling on — our users mix Vietnamese and English in the same sentence. Ten slots per field is plenty; treat unused slots as wasted accuracy.
How-to

Standing up a Genie space on a metric view

1

Build & grant the view

Create the metric view in the gold schema. GRANT SELECT to the consuming group — Genie runs as the user.

2

Create the space

New Genie space → add the metric view as the data asset. Same flow as adding a table.

3

Verify what surfaced

Confirm the fields and measures appear with their display names. If they don't, the YAML metadata is missing.

4

Add sample questions

Seed the space with the five questions the audience will genuinely ask first.

5

Add example SQL — sparingly

Only for multi-step questions the measures can't express on their own.

6

Benchmark it

Turn validated questions into benchmark questions and score accuracy over time.

Prove the migration: run the same benchmark set against the old space and the metric-view space. That number is the business case, and it takes an afternoon.

Watch for the ceiling

A space caps at 30 tables and performs best at five or fewer. Collapsing a star schema into one metric view is often the cheapest way back under that line.

Step 3 catches most problems immediately — if display names and synonyms aren't showing, nothing downstream will work. Step 6 is the one teams skip; make it a requirement for sign-off.
Recommended

The pattern we should standardise on

1

A metric view as the KPI backbone

Every governed number the business quotes. This is what most questions resolve against.

2

One curated view for drill-down

A narrow, well-commented row-level view for "show me the actual records". Metric views can't be joined to it — it's a separate asset, and that's fine.

3

A handful of example SQL queries

Reserved for genuinely multi-step questions. Not a dumping ground for metric definitions.

4

Text instructions only for etiquette

Fiscal calendar conventions, default currency, "always show the period". Not business logic.

Why this shape works

The aggregate questions — which is most of them — hit a governed definition. The detail questions have somewhere legitimate to go. And the space stays far under the asset ceiling.

a typical TCB spaceassets
# 2 assets, not 7
tcb.gold.mv_sales          # metric view — KPIs
tcb.gold.v_order_detail    # view — row-level drill-down

# + 3 example SQL queries
# + 4 text instructions (fiscal calendar, currency)
Sequence matters: model the metric view first. Anything you still can't answer becomes an example query — not the other way round.
This is the actionable takeaway. If people leave with one diagram in their heads, make it this one. Emphasise the sequence in the last callout — teams that start with example queries never get around to modelling.
Field notes

What goes wrong, and what it means

What you seeActual causeFix
Genie ignores the metric view and picks a tableBoth are in the space and the raw table looks "closer" to the questionRemove the redundant table, or narrow it to a drill-down view
Answers change between rephrasingsThe metric isn't defined anywhere — Genie re-infers each timeMove that metric into the metric view as a measure
Numbers inflate after adding a dimensionJoin fan-out — the "dimension" isn't unique on the keyVerify cardinality before at_most_one_match: true
Genie can't find a field users clearly namedBusiness vocabulary never reached the modelAdd it to synonyms — up to 10 per field
"Show me order 12345" returns nothing usefulThe space only has a metric view; it can't return rowsAdd the curated drill-down view
Slow or scattered asset selectionToo many assets in the spaceCollapse the star schema into one metric view; aim for ≤5
Text instructions contradict each otherLogic accumulated in tier 3 instead of tier 1Promote the rules into measures, filters and fields
Row three is the dangerous one. It doesn't throw an error — it returns a bigger, confidently-presented number. Always reconcile after adding a join.
Row one surprises people constantly: leaving the source tables in the space alongside the metric view actively undermines it. Cleaning up the asset list is often the single highest-impact fix.
Recap

Four things to take away

1

Genie only knows what you give it

It writes SQL from context. Missing semantics get invented, plausibly.

2

A puts meaning in the space

Fast to start, fragile at scale, re-done for every new space, fails quietly.

3

B puts meaning in the catalog

Modelled once, governed, reusable, correct at any grain — fails loudly.

4

Run both, deliberately

Metric view for KPIs, one curated view for detail, example SQL only for the rest.
